# Докинг как источник сигнала: методологическое исследование смещений

## Цель работы

Это **не** проект по поиску лекарств. Это методологическое исследование одного
вопроса: можно ли доверять докинг-скору AutoDock Vina как сигналу для reward
в генеративных моделях, учитывая известный факт, что скор Vina коррелирует с
размером молекулы независимо от реального связывания.

Центральная гипотеза: **величина размерного смещения (R² регрессии
score~heavy_atoms) зависит от геометрии кармана связывания** — открытые/большие
карманы должны показывать смещение сильнее, чем тесные/закрытые. Объясняющая
переменная — геометрия кармана (дескрипторы fpocket); зависимая — величина
смещения.

## Протокол: 18 тестов, 8 стадий

| Стадия | Тесты | Что проверяет |
|---|---|---|
| 0 | 1-4 | Смещение в самом датасете (до докинга): физхим-свойства актив/декой, ligand-only baseline, AVE bias, аналоговое смещение скэлдов |
| 1 | 5 | **ЕДИНСТВЕННЫЙ гейт**: redock RMSD < 2.0Å на свежем конформере (не координаты кристалла) |
| 2 | 9-10 | Собственный шум Vina по сидам; чувствительность к exhaustiveness |
| 3 | 7,11-14 | Label-shuffle null-модель, screening/ranking power, **Test A' — главный результат** (размерное смещение), ligand efficiency |
| 4 | 15 | PoseBusters на сохранённых позах |
| 5 | 6,8 | Cross-docking на альтернативные структуры; receptor-decoy site (докинг в заведомо неправильный карман) — дорогие, только по явной команде |
| 6 | 16 | PoseCheck на сырых позах генеративной модели (Test B) — только по явной команде |
| 7 | 17-18 | Дескрипторы кармана (fpocket); **главный вывод** — регрессия величины смещения на геометрию кармана |

**Правило исключения**: единственная законная причина остановить обработку
мишени — провал Stage 1 (redock RMSD ≥ 2.0Å). Все остальные 17 тестов
**никогда** не исключают мишень — плохой результат помечается флагом и
считается дальше. Обоснование: исследование ищет связь между провалом
и геометрией кармана; исключение по результату разрушило бы саму эту связь.

Все пороги и параметры — в `config/protocol.yaml`, ничего не захардкожено в
коде.

## Структура репозитория

```
controls/                  18 тестов, по одному файлу на тест + оркестратор
  run_controls.py            запуск стадий: python controls/run_controls.py GENE --stage N
  test01..test18_*.py        реализация каждого теста
  protocol.py                общая инфраструктура (конфиг, resume, сохранение)
config/protocol.yaml       все пороги/параметры
run_test_a.py               основной скрининг-пайплайн (Test A): build/dock/analyze/funnel
dock_existing_candidates.py ядро докинга (Vina + опционально gnina CNN-рескоринг)
run_redock.py               базовая redock-валидация
run_fpocket.py               дескрипторы кармана через fpocket (WSL)
module_generative/          генеративный цикл (не входит в 18-тестовый протокол)
DiffSBDD/                    генерация лигандов (Test B) - клонированный внешний проект, не в репо

```

## Реальные находки (не итоговые, но уже интересные)

- **PIK3CA**: размерное смещение слабое (R²=0.036), реальный сигнал докинга
  устойчив после учёта размера (partial correlation значима, p<1e-19).
- **CDK2**: обратная картина — R²=0.589 (провал порога 0.5), сырой Vina-скор
  вообще неотличим от случайного шума (permutation p=0.687) без gnina-рескоринга.
- **BRAF**: после исправления перекоса по logP в декоях (см. ниже) и честного
  теста без утечки данных (Test 8) — BEDROC в правильном кармане (0.775) и в
  заведомо неправильном (0.752) почти совпадают. Докинг слабо отличает
  специфичное связывание от случайного попадания на этой мишени.

Эти три точки уже показывают качественно разное поведение между мишенями —
ровно то, что должен объяснить Test 18, когда наберётся достаточно данных.

## Известные ограничения / чиненные баги

Список сохраняется намеренно — часть научной честности процесса:

- Обрезка DUD-E декоев была через первые N строк файла (не случайно), что
  ломало property-matching по logP — исправлено на случайную подвыборку.
- Test 8 (receptor-decoy site) изначально отбирал топ-кандидатов по скору
  в ПРАВИЛЬНОМ кармане перед тестом на НЕПРАВИЛЬНОМ — data leakage,
  искусственно завышавший результат. Переделан на фиксированный набор
  (все активные + случайные декои), не зависящий ни от одного скора.
- Test 5 (гейт) не различал "не прошёл по RMSD" и "упал с ошибкой" (например,
  из-за отключённого интернета) — обе ситуации выглядели одинаково и
  пропускали дальнейшие стадии без объяснения. Разведено на статусы
  `pass`/`fail`/`error`.
- Докинг в новых тестах (9/10/8) не ограничивал `--cpu` на воркер, что при
  параллельном запуске нескольких пулов давало oversubscription и резкое
  падение успешности докинга (наблюдалось падение с 100% до 23% на одном
  прогоне). Исправлено по образцу основного пайплайна.

## Железо и ограничения

8GB RAM, GTX 1650 Ti (4GB VRAM), Windows 11 + WSL2 Ubuntu (gnina, fpocket).
Генерация (DiffSBDD) и тяжёлый параллельный докинг не должны запускаться
одновременно — конкуренция за RAM вызывает падения (Segmentation fault
у генерации, наблюдалось и воспроизведено).
